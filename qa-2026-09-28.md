## Does `GFX.md` say how to pick the window and device backend?

Yes, in a table at lines 72-73, with an example at line 79:

| Variable | Values | Default |
|---|---|---|
| `WOW_GFX_WINDOW` | `x11`, `sdl`, `glfw`, `win32` | the first the library has: x11, win32, glfw, sdl |
| `WOW_GFX_DEVICE` | `gl4`, `gl3`, `gles3`, `vk`, `d3d11`, `d3d12` | the first the library has: gl4, gl3, d3d11, gles3, vk, d3d12 |

```sh
WOW_GFX_WINDOW=sdl WOW_GFX_DEVICE=vk cargo run --release -p benilla --features gfx
```

On Linux the default is x11 with gl4. An unavailable combination fails at boot with a message
naming the choices; it never falls back silently.

`GFX.md`'s Linux row in the pair table (line 86) still says "no live server login yet", which
this run made stale.

## Were gl3 and gles3 tested, or only vk and gl4?

All four devices were tested live on all three Linux windows. All 12 pairs (x11, sdl and glfw,
each with gl3, gl4, gles3 and vk) logged into the world with no errors or panics.

The player portrait was compared against wgpu on each pair:

- **vk:** matches (max 1 level).
- **gl3, gl4, gles3:** 0.79% of the portrait's pixels are 1-2 levels off, the same on all three.
  This is the radeonsi GL sRGB rounding already noted in `progress.md`.

Two checks were narrower:

- **Character screen:** only x11 gl4 and x11 vk.
- **Frame-cost, MSAA and paper-doll runs:** only gl4 and vk.

## Were there FPS differences between wgpu and the tested devices?

Yes, measured for three setups: wgpu, gfx vk and gfx gl4, all on the x11 window. gl3, gles3 and
the sdl and glfw windows were not measured.

Each ran with vsync off, standing still in the same Durotar spot, sampling 600 frames after a
warm-up (`WOW_LIVE_FPS=600 WOW_GPU_MS=1`):

| Build | FPS | Mean frame | p99 frame | GPU time (median) | CPU time per frame |
|---|---|---|---|---|---|
| wgpu | 54.8 | 18.25 ms | 20.23 ms | 5.87 ms | 33.0 ms |
| gfx vk | 74.6 | 13.40 ms | 17.06 ms | 6.46 ms | 15.1 ms |
| gfx gl4 | 91.9 | 10.89 ms | 12.89 ms | 5.44 ms | 13.5 ms |

The GPU does about the same work on all three. The gfx builds are faster because they spend far
less CPU time per frame, not because anything draws faster.

These are single runs of a quiet scene, so the ranking is indicative. A busy area (a city, many
particles) or a run while moving (`WOW_LIVE_FPS_MOVE=1`) could spread the numbers differently.
The same measurement can be run for gl3, gles3 and the sdl and glfw windows.

## How extensive are the changes in `gfx_benilla`? Is it close to `gfx_dll/gfx`?

It is still close. The changes are mostly additions: about 5,800 lines added and about 270
removed or changed, across 43 files, in 17 commits in the gfx repo.

**Size in context:** gfx's own C code is roughly 35-40k lines, not counting the vendored Vulkan,
GL and VMA headers. The diff is around 15% on top, almost all of it new code beside the
original rather than rewrites. No original function signature changed. The DLL surface in
`gfx_dll.h` grew from 99 to 122 functions, all additions.

**Where the lines are:**

| Area | Added / removed | Main files |
|---|---|---|
| Device backends | ~2,500 / ~120 | `vk.c` 947/94, `gl.c` 511/4, d3d12 367, d3d11 318, gles3/gl3/gl4 ~140 each |
| Window backends | ~1,700 / ~150 | `x11.c` 814/68, `win32.c` 314/70, `sdl.c` 305, `glfw.c` 224 |
| Plumbing | ~1,000 / 0 | new ops wired through `gfx_dll.c/h`, `device.c/h`, `window.c/h`, `objects.h`, and small stubs in each backend |

**What the changes do** (the full list is in `progress.md`'s build notes and the gfx repo's git
log):

- **New API:**
  - rasterizer depth bias
  - reading back and copying textures, and partial-texture updates
  - sRGB and 32-bit float depth formats
  - asking the device which texture formats it supports
  - GL clip settings, so GL matches Bevy's clip space and draws top-down like vk
  - vk multisampling and resolve
  - GPU timestamps
- **Window and input:**
  - physical keys and scancodes, raw mouse motion, display scale factor
  - cursor visibility, grab, warp and icon
  - window mode, level, position, centring, decorations and resizable
  - windows created unmapped
- **Bug fixes in the original gfx:**
  - vk: sampler-slot mapping and descriptor fill, depth barriers, offscreen passes that now load
    their contents, the memory allocator never freed at teardown
  - GL: the depth attachment and 32-bit depth format, array depth on gl3/gles3, clears that
    ignored write masks
  - window backends: several input quirks on x11, glfw, sdl and win32

The bug fixes are the best candidates to upstream into `gfx_dll/gfx`: they are not
benilla-specific, and `progress.md` lists them as upstream candidates.

The win32, d3d11 and d3d12 parts (about 1,000 of the added lines) were written without being
built, since the Linux machine cannot compile them. Everything else was built and run on Linux.
